Forst extends familiar Go syntax with **structural typing**, **constraints**, and **narrowing**. Most `.ft` files look like Go. Where they differ, types behave like validated API schemas.

## Aligned with Go

Ordinary Forst programs look like Go. A minimal executable is identical on both sides:

Use **`.ft`** files with the Forst CLI. The plain Go subset builds with `go build`. Forst extensions transpile to Go for production.

## Explicit where it matters

Forst embraces inference in clear cases (return types, obvious locals) but requires explicit annotations where ambiguity would hurt reliability:

- Function **parameters** always declare types
- Struct **fields** always declare types
- **Nil** initializations need an explicit type

## Control flow you can trace

Forst has no exceptions. Failures do not jump out of the call stack, so you can read a function top to bottom and see every way it can fail.

Expected failures are values you declare with the **`error`** keyword. Callers handle a named type instead of parsing a message. Checks use **`ensure`** and **`is`**, so validation sits next to the code that depends on it.

See [Check a value](/language/check-a-value) and [Return a named error](/language/named-errors).

## Packages and imports

Forst uses Go style **packages** and **`import`** paths. You can also **import Go packages** and call qualified functions (`fmt.Println`, etc.). See [Go interop](/interop/go) for current limits.

For the Go target, **one directory holds one Forst package**, and **one package name lives in one directory**. You may split a package across **multiple `.ft` files in that directory** (for example `auth/auth.ft` and `auth/bcrypt.ft`, both `package auth`). The same `package` name in **sibling directories** is a compile error. Different package names in the same folder (for example `main.ft` and `auth.ft` together) are also rejected, matching Go.

## File layout in a typical backend

A mixed Forst and Go service often looks like this:

```text
my-service/
├── go.mod
├── handlers/
│   ├── orders/
│   │   └── orders.ft      # package orders
│   └── catalog/
│       └── catalog.ft     # package catalog
├── auth/
│   ├── auth.ft        # package auth
│   └── bcrypt.ft      # package auth (multi-file, one directory)
├── internal/
│   └── legacy.go      # existing Go code
├── ftconfig.json      # generate / dev discovery
└── .forst/client/     # forst generate output (gitignored, linked as @forst/gen)
```

## Caveats

Forst is not a full Go clone. Several areas are experimental or intentionally different.

- **No `panic` / `recover` / `try` / `catch`** as language features. Generated Go may still call panicking third party code.
- **Go import loading** is partial. See [Mix with Go packages § Caveats](/interop/go#caveats).
- **Validation and narrowing** have real limits. See [Describe a shape](/language/shapes-and-constraints#caveats), [Check a value](/language/check-a-value#caveats), and [Return a named error](/language/named-errors#caveats).
